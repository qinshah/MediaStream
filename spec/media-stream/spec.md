# Feature Specification: 手机录屏与 RTMP 直播推流（media_stream 模块化解耦）

**Created**: 2026-09-20  
**Status**: Draft  
**Input**: User description: "这是一个新建的鸿蒙 hap 项目，而 Harmony-OBS-Studio 是一个适配了鸿蒙的 obs 部分的代码。现在你需要让当前项目支持录屏和推直播流。native 部分可解耦到 ./media_stream 模块。（要求支持手机设备）"

## Overview

为现有 HarmonyOS 手机应用（MediaStream）提供屏幕采集能力，并输出为两条可独立或同时使用的链路：**本地录屏**（采集 → 硬件编码 → MP4 文件保存至应用沙箱）与**直播推流**（采集 → 硬件编码 → 自定义 RTMP 地址推流）。所有采集、编码、封装、推流的原生实现解耦到 `media_stream` 模块；`entry` 仅承担 ArkUI 界面、权限申请与会话控制。原生实现借鉴仓库内 Harmony-OBS-Studio（AirCast 鸿蒙化工作树）中 `ohos-capture`（AVScreenCapture 采集适配）、`ohos-audio`、`obs-outputs/librtmp`（RTMP 协议栈）的已验证经验，但**不引入 libobs/FFmpeg/Qt 全量运行时依赖**（经用户确认采用轻量自研管线）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 配置并开始 RTMP 直播推流 (Priority: P1)

用户在控制台页输入自定义 RTMP 推流地址，选择音频源（仅麦克风 / 仅系统内录 / 麦克风+内录），点击"开始推流"。系统弹出录屏授权弹窗，用户同意后，屏幕画面与所选音频被实时编码（H.264/AAC）并推送到目标 RTMP 服务器。推流过程中页面实时显示会话状态（连接中 / 推流中 / 已停止 / 错误及原因）、已推流时长、码率/帧率与已发送数据量。用户点击"停止推流"后会话正常收尾。

**Why this priority**: 直播推流是本次需求两大核心目标之一，是产品对外的核心价值；无此故事则功能不成立。

**Independent Test**: 在局域网部署任一标准 RTMP 服务器（如 SRS/nginx-rtmp），仅依赖本故事即可用任意播放器（ffplay/VLC）拉流验证画面与声音，不依赖录制功能。

**Acceptance Scenarios**:

1. **Given** 有效 RTMP 地址与可达网络，**When** 用户点击"开始推流"并在系统弹窗中同意录屏，**Then** 应用进入"推流中"状态，拉流端在 5 秒内出现画面与所选音频，时长/码率统计开始刷新。
2. **Given** 推流进行中，**When** 用户点击"停止推流"，**Then** 会话正常关闭（RTMP 协议正确收尾），状态回到"已停止"，再次点击"开始推流"可发起新会话。
3. **Given** 无效 RTMP 地址或服务器不可达，**When** 用户点击"开始推流"并授权录屏，**Then** 自动重连至多 3 次（指数退避）后停止并展示明确错误原因，应用不崩溃。
4. **Given** 用户在系统弹窗中拒绝录屏授权，**When** 授权流程返回，**Then** 会话终止并给出引导提示，不残留"推流中"状态。

---

### User Story 2 - 本地录屏生成 MP4 (Priority: P1)

用户在控制台页点击"开始录制"，同意系统录屏授权后，屏幕画面与所选音频源被实时编码并封装为 MP4 文件，保存至应用沙箱 `files/videos` 目录（文件名含录制起始时间戳）。录制中页面显示录制时长与文件预估大小。点击"停止录制"后文件完整落盘，并出现在录制列表中。

**Why this priority**: 本地录屏是另一核心目标，且是独立可交付的最小价值单元（与推流互不依赖）。

**Independent Test**: 无需任何流媒体服务器，仅依赖本故事即可在录制列表中找到产物并用系统播放器播放验证，完全独立于推流功能。

**Acceptance Scenarios**:

1. **Given** 用户已同意录屏授权，**When** 点击"开始录制"，**Then** 状态变为"录制中"，时长开始累计。
2. **Given** 录制进行中，**When** 点击"停止录制"，**Then** 生成完整可播放的 MP4（视频 H.264 + 所选音频 AAC），保存于应用沙箱 videos 目录，文件出现在录制列表。
3. **Given** 设备存储空间不足，**When** 录制进行中，**Then** 会话安全停止并提示存储不足，不产生损坏文件。

---

### User Story 3 - 边推流边录制 (Priority: P2)

推流会话进行中，用户点击"开始录制"，同一采集编码流被同时分发到 RTMP 输出与 MP4 封装输出，两路输出可各自独立停止；反向（录制中开始推流）同样支持。

**Why this priority**: 单编码流分发成本低、价值高（直播回放素材一键留存），但非最小可用集的核心。

**Independent Test**: 依赖故事 1 与故事 2 完成后组合验证：推流中开启录制，5 分钟后两路输出均正常且拉流端无可感知卡顿。

**Acceptance Scenarios**:

1. **Given** 推流进行中，**When** 用户点击"开始录制"，**Then** MP4 输出开始，RTMP 推流不中断、无明显卡顿，两路状态独立显示。
2. **Given** 同时推流+录制中，**When** 仅点击"停止录制"，**Then** MP4 正常收尾，推流继续。

---

### User Story 4 - 录制文件列表管理 (Priority: P2)

用户进入"录制列表"页，按时间倒序查看所有录制文件（文件名、时长、大小、创建时间），可播放（调起系统播放器）、删除（带确认）、分享（系统分享面板）。

**Why this priority**: 让录制产物可用、可管理，闭环录屏体验；但 MVP 可先通过文件管理器访问沙箱目录。

**Independent Test**: 依赖故事 2 产生的文件即可独立验证列表、播放、删除、分享四项操作。

**Acceptance Scenarios**:

1. **Given** 存在至少 1 个录制文件，**When** 打开录制列表，**Then** 列表按创建时间倒序展示文件名、时长、大小。
2. **Given** 列表页，**When** 点击某文件"播放"，**Then** 调起系统播放器正常播放。
3. **Given** 列表页，**When** 删除某文件并确认，**Then** 文件从列表与沙箱中移除。
4. **Given** 列表页，**When** 分享某文件，**Then** 弹出系统分享面板并可将文件传出。

---

### User Story 5 - 采集参数配置与持久化 (Priority: P2)

用户在控制台页选择画质预设（分辨率/帧率/视频码率）与音频源档位；填写 RTMP 地址。所有配置在下次启动应用时自动恢复上次取值。

**Why this priority**: 面向真实直播场景的必要个性化能力，但默认预设已可开箱即用。

**Independent Test**: 修改配置 → 杀进程重启 → 验证配置恢复；修改预设后发起会话验证输出参数生效（拉流端分辨率/码率）。

**Acceptance Scenarios**:

1. **Given** 控制台页，**When** 用户切换画质预设与音频源并填写 RTMP 地址，**Then** 立即持久化保存。
2. **Given** 已保存配置，**When** 完全退出应用后重新打开，**Then** 配置项恢复为上次取值。
3. **Given** 选择 720p 预设，**When** 发起推流，**Then** 拉流端画面为 720p，码率符合预设档位。

---

### User Story 6 - 网络中断自动重连 (Priority: P3)

推流过程中网络抖动/断开时，应用自动按指数退避策略重连（默认最多 3 次）；重连期间状态显示"重连中 (n/3)"；任一时刻用户可手动停止。恢复成功后推流继续且无需重新授权录屏。

**Why this priority**: 提升直播可用性，但基础推流（故事 1）已交付核心价值。

**Independent Test**: 推流中开关飞行模式/Wi-Fi，观察自动重连与状态展示。

**Acceptance Scenarios**:

1. **Given** 推流进行中，**When** 网络断开，**Then** 状态转为"重连中 (1/3)"并开始退避重试。
2. **Given** 重连期间网络恢复，**When** 重连成功，**Then** 推流继续且采集会话未中断（无需再次授权）。
3. **Given** 连续 3 次重连均失败，**When** 达到上限，**Then** 会话停止并提示"网络异常，推流已停止"。

---

### Edge Cases

- **录屏授权弹窗被系统关闭/超时**：视为拒绝授权处理，会话终止并提示。
- **所选音频源包含麦克风但麦克风被系统开关禁用/权限被拒**：按能力降级（如仅内录或无音频）并明确提示降级原因，会话不中断。
- **设备来电/出现隐私窗口**：采集内容按系统策略处理（隐私画面由系统屏蔽），会话保持；若系统强制终止会话，应用正确回收资源并提示。
- **采集期间屏幕旋转**：会话不中断，v1 按采集原始方向输出，不动态重建编码器。
- **重复快速点击开始/停止按钮**：按钮防重入，不产生状态错乱或资源泄漏。
- **应用被杀进程/崩溃后重启**：残留的部分写入文件在下次进入录制列表时被识别为无效文件并提示可清理，不显示为可用项。
- **RTMP 服务器中途主动断开连接**：与网络中断同样走自动重连流程。
- **内录档位下系统无任何媒体播放**：输出静音音频轨，会话正常。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持全屏采集手机屏幕视频原始流，采集参数（分辨率/帧率/码率）由所选画质预设决定（预设：1080p/30fps/8Mbps、720p/30fps/4Mbps、480p/30fps/2Mbps，可扩展）。
- **FR-002**: 系统 MUST 支持三档音频源采集：仅麦克风 / 仅系统内录 / 麦克风+内录，音频规格为 48kHz 双声道；且 MUST 支持在会话发起前切换档位。
- **FR-003**: 系统 MUST 使用设备硬件编码器将采集视频编码为 H.264、音频编码为 AAC，编码参数与所选预设一致。
- **FR-004**: 系统 MUST 支持将编码流经 FLV/RTMP 协议推送到用户输入的任意自定义 RTMP URL（rtmp:// 格式校验）。
- **FR-005**: 系统 MUST 支持将编码流封装为 MP4 文件（H.264+AAC），保存至应用沙箱 videos 目录，文件名含录制起始时间戳。
- **FR-006**: 系统 MUST 支持同一编码流同时分发至 RTMP 推流输出与 MP4 录制输出，且两路输出可独立启停（含"录制中开始推流"与"推流中开始录制"双向场景）。
- **FR-007**: 系统 MUST 提供会话状态实时上报：连接中 / 推流中 / 录制中 / 重连中(n/N) / 已停止 / 错误（含原因文案），以及时长、已发送数据量、实时码率/帧率统计。
- **FR-008**: 系统 MUST 在推流连接异常中断时自动重连：指数退避，默认最多 3 次；重连期间采集会话保持，无需用户重新授权。
- **FR-009**: 系统 MUST 持久化用户配置（RTMP 地址、画质预设、音频源档位），应用冷启动后恢复。
- **FR-010**: 系统 MUST 提供录制文件列表（按创建时间倒序：文件名、时长、大小），并支持播放（系统播放器）、删除（带确认）、分享（系统分享面板）。
- **FR-011**: 系统 MUST 正确处理授权链路：录屏授权由系统弹窗承载；拒绝授权时会话终止并给出引导提示；麦克风不可用时按能力降级并明确提示。
- **FR-012**: 系统 MUST 保证采集/编码/推流/录制会话在应用退后台或锁屏后持续运行（按系统要求申请对应长时任务）。
- **FR-013**: 系统 MUST 将所有原生能力（采集、编码、封装、RTMP 协议、会话状态机）实现于 `media_stream` 模块内，通过该模块的 ArkTS API + 事件回调对外暴露；`entry` 模块 MUST NOT 包含任何媒体处理原生实现，仅做 UI、权限申请与调用编排。
- **FR-014**: 系统 MUST 在会话停止、页面销毁、应用退出时正确释放全部原生资源（采集、编码器、封装器、网络连接），重复启停无资源泄漏与崩溃。
- **FR-015**: 系统 MUST 对并发与重入做防护：重复开始、未开始即停止、停止中再操作等均安全忽略或给出状态提示。

### Key Entities

- **CaptureSession（采集会话）**: 屏幕视频 + 选定音频源的采集实体；状态机：idle → authorizing → running → stopped / error；一个会话可挂接至多两个输出（RTMP、MP4）。
- **StreamOutput（推流输出）**: 绑定一个 RTMP URL；跟踪连接状态与推流统计（时长、字节、码率、帧率、重连次数）。
- **RecordOutput（录制输出）**: 绑定一个 MP4 文件路径；跟踪录制时长与文件大小。
- **OutputConfig（输出配置）**: 画质预设（分辨率/帧率/视频码率）、音频源档位、RTMP 地址；可持久化。
- **RecordingFile（录制文件）**: 文件名、沙箱路径、时长、大小、创建时间；列表展示与播放/删除/分享操作的实体。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 真机完成 ≥10 分钟的 1080p/30fps RTMP 推流会话，拉流端画面持续流畅、无花屏、音画同步，全程无崩溃。
- **SC-002**: 录制 ≥5 分钟生成可被系统播放器正常播放的 MP4，音轨与所选音频源一致。
- **SC-003**: 同时推流+录制 5 分钟，两路输出均完整可用，相比单路推流无可感知卡顿。
- **SC-004**: 推流中断网后恢复场景，自动重连成功率 ≥90%，单次恢复耗时 ≤15 秒。
- **SC-005**: 全部异常场景（拒绝录屏授权、麦克风不可用、无效 URL、服务器不可达、存储不足、重复启停）均给出明确中文提示，应用零崩溃。
- **SC-006**: 应用退后台或锁屏后，采集会话持续 ≥5 分钟不中断。
- **SC-007**: 1080p/30fps 会话期间整机功耗可控（硬件编码生效，无明显发热降频导致掉帧）。

## Assumptions

- 目标设备为**手机（phone）**；工程 compatibleSdkVersion 为 6.1.0(API 23)、targetSdk 为 API 26，所用系统能力（AVScreenCapture 原始流 C API、硬件编解码 C API、MP4 封装 C API、长时任务）版本均满足。
- 经用户确认采用**轻量自研原生管线**：`media_stream` 内直接使用 OHOS NDK（AVScreenCapture → OH_VideoEncoder/OH_AACEncoder → OH_AVMuxer + RTMP 协议栈），借鉴 Harmony-OBS-Studio 的 `ohos-capture`/`ohos-audio`/`librtmp` 适配经验；不引入 libobs、FFmpeg、x264、Qt 等外部运行时依赖。
- v1 仅支持全屏采集（单场景）；不含 RTMPS/SRT、不含 OBS 场景切换/滤镜/多源混流等高级能力（后续版本可扩展）。
- MP4 保存于应用沙箱（清除应用数据将删除录制文件）；分享通过系统分享面板完成，不自建上传服务。
- 采集期间屏幕旋转不中断会话、不重建编码器，按采集原始方向输出。
- 录屏授权由 `AVScreenCapture` 的系统授权弹窗承载（无需应用自定义授权 UI）；麦克风依赖系统麦克风权限与开关状态。
- 推流验证依赖用户自备的标准 RTMP 服务器（如局域网 SRS/nginx-rtmp）；本工程不内嵌服务端。
- UI 基础交互可在模拟器验证；采集/编码/推流全链路验证需真机。

## Open Questions

- 无关键未决项（原生路径、输出格式与位置、协议与音频源、UI 范围、边推边录、后台行为均已通过两轮需求澄清确认）。
- 次要待实现阶段按系统规范确认项：长时任务类型与常驻通知的具体系统要求（影响通知栏展示形态，不影响需求范围）。
